
# Kudo 模型配置与任务文件格式设计

## 1. 文档定位

本文是 Kudo 及其业务宿主共同使用的模型配置、画布属性、图元属性、模型扩展属性和任务文件格式基线。

本文统一定义：

- 任务目录和 mdl 单文件包的结构；
- Task.xml 的通用文档结构；
- 画布运行时状态和 Viewport 持久化；
- 普通图元和个性化图元的属性描述格式；
- 属性分组、表单编辑器、下拉选项和显示条件；
- 配置文件和任务文件的校验结果模型；
- 启动配置检查和打开任务文件检查的处理方式；
- 国际化 Key、稳定标识和 NativeAOT 约束。

宿主项目只能增加 XML 数据、资源和模型扩展实现，不能修改 Kudo 通用格式来表达某一个特定领域的图元。

## 2. 设计边界

Kudo 负责：

- 任务文件和任务目录；
- 画布、节点、端口、连线、分组和注释的通用模型；
- 任务文件的序列化、反序列化和结构校验；
- 画布 Viewport 的保存和恢复；
- 通用属性 Schema 的解释；
- 配置问题和任务文件问题的通用诊断模型；
- 通用问题列表和恢复操作的承载接口。

业务宿主或模型扩展负责：

- 模型库分类和图元入口数据；
- 个性化图元状态；
- 业务属性的动态值；
- 动态表格行；
- 业务校验；
- 个性化端口；
- 绘制描述和样式。

Kudo 不判断 ExpansionMode、SegmentCount、RelativeAngle 等业务属性的含义。Kudo 只根据通用属性描述生成界面并提交属性值。

## 3. 标识和国际化

### 3.1 持久化标识

XML 节点名、XML 属性名、属性组标识、属性标识、下拉选项值和表格行标识使用 PascalCase。

标识必须：

- 稳定；
- 与语言无关；
- 不使用 C# 类型全名；
- 不使用程序集名称；
- 不使用显示文本；
- 不使用数组下标作为唯一身份。

示例：

    HydraulicPipe
    ExpansionMode
    FullyExpanded
    RelativeAngle
    Segment01

### 3.2 国际化

配置 XML 和任务文件中不保存用户可见的中文或英文文本，使用资源 Key：

    TitleKey
    DescriptionKey
    DisplayKey
    PlaceholderKey
    HelpKey

下拉选项示例：

    <Option Value="FullyExpanded"
            DisplayKey="Models.Hydraulics.Pipe.ExpansionMode.FullyExpanded" />

语言切换时，属性标识和任务值不变，只重新解析资源并刷新显示内容。

## 4. 配置文件布局

业务宿主可以在发布目录提供以下通用布局：

    Models/
    ├─ Model.xml
    └─ Symbols/
       ├─ BasicSymbols.Valve.xml
       ├─ Hydraulics.Pipe.xml
       └─ ...

Model.xml 只负责模型库分类和图元入口。Symbols 目录内的所有图元文件必须使用同一个通用 SymbolDefinition 格式。画布属性不属于模型库配置，由任务文件中的 CanvasSettings 和 Viewport 保存。

国际化资源由宿主和模型扩展共同提供，发布后统一进入 I18n 目录。资源 Key 使用模块命名空间，避免不同宿主项目冲突。

## 5. 通用属性描述

所有画布和图元属性使用相同的描述结构：

| 元素 | 作用 |
| --- | --- |
| PropertyDefinition | 定义属性类型、编辑器、标题、默认值和校验 |
| PropertyGroup | 定义属性分组、标题和顺序 |
| PropertyRef | 将属性放入一个分组 |
| Option | 定义下拉选项值和显示 Key |
| Visibility | 定义通用显示条件 |
| Validation | 定义通用校验规则 |
| Table | 定义集合属性的表格 |
| Column | 定义表格列 |
| Presentation | 区分创建对话框和属性栏的行为 |

属性定义和属性分组分离。一个属性可以被多个分组引用，但任务文件只保存一份属性值。

属性定义示例：

    <PropertyDefinition Id="PropertyId"
                        ValueType="String"
                        Editor="TextBox"
                        TitleKey="Namespace.Property.Title"
                        DescriptionKey="Namespace.Property.Description"
                        DefaultValue=""
                        ReadOnly="false" />

属性分组示例：

    <PropertyGroup Id="GroupId"
                   TitleKey="Namespace.Group.Title"
                   Order="10"
                   IsVisible="true">
      <PropertyRef PropertyId="PropertyId" />
    </PropertyGroup>

## 6. 画布属性和任务视口

画布属性由 Kudo 的 GraphCanvasSettings 和 GraphGridSettings 表示，任务文件通过 CanvasSettings 和 Viewport 保存当前任务的画布状态。模型库不提供独立的画布配置文件。

第一版建议提供三个用户可见分组。

### 6.1 Viewport

| 属性 | 编辑器 | 说明 |
| --- | --- | --- |
| Zoom | TextBox | 当前缩放比例 |
| OffsetX | TextBox | 当前水平偏移 |
| OffsetY | TextBox | 当前垂直偏移 |

### 6.2 Grid

| 属性 | 编辑器 | 说明 |
| --- | --- | --- |
| GridVisible | CheckBox | 是否显示网格 |
| GridSize | TextBox | 网格间距 |
| SnapEnabled | CheckBox | 是否启用吸附 |
| SnapSize | TextBox | 吸附间距 |

### 6.3 Display

| 属性 | 编辑器 | 说明 |
| --- | --- | --- |
| ShowPorts | CheckBox | 是否显示端口 |
| ShowPortLabels | ComboBox | 端口标签显示方式 |
| ShowNodeNames | CheckBox | 是否显示图元名称 |
| ShowMinimap | CheckBox | 是否显示缩略图 |

LOD 阈值和渲染缓存属于 Kudo 高级设置。可以放入 Advanced 分组，但默认隐藏或只读。

Viewport 是任务状态的一部分。保存任务时保存当前 Viewport，打开任务并完成节点恢复后再应用 Viewport。

## 7. 通用图元属性定义

### 7.1 Basic 分组

| 属性 | 编辑器 | 说明 |
| --- | --- | --- |
| Name | TextBox | 图元名称 |
| Position | PointEditor | 显示为 [X,Y]，展开后编辑 X、Y |
| Size | SizeEditor | 显示为 [Width x Height]，展开后编辑长度和宽度 |
| Locked | CheckBox | 是否锁定 |

PointEditor 和 SizeEditor 是通用布局描述，内部仍使用普通 TextBox，不增加数字微调控件。

### 7.2 Appearance 分组

| 属性 | 编辑器 | 说明 |
| --- | --- | --- |
| BackgroundImage | ComboBox 或 TextBox | 资源标识 |
| NameDisplayMode | ComboBox | 名称显示方式 |
| PortLabelDisplayMode | ComboBox | 端口标签显示方式 |
| InternalPropertyDictionary | KeyValueTable | 默认只读 |

InternalPropertyDictionary 默认只读。只有确实允许用户修改内部属性的图元，才在 XML 中设置 ReadOnly 为 false。

普通图元的端口数量、位置、方向和连接容量由图元 XML 配置。端口不是普通用户属性，除非后续专门增加端口编辑能力。

## 8. 个性化图元属性定义

个性化图元不能创建业务专用 XML 结构。禁止设计只为管道存在的 HydraulicPipe、PipeSegments 等专用节点。

个性化图元继续使用：

    PropertyDefinition
    PropertyGroup
    PropertyRef
    Option
    Table
    Column
    Visibility
    Validation

管道只是使用通用结构定义自己的属性 Key。Kudo 不识别这些 Key 的业务含义。

管道建议使用两个属性组。

### 8.1 Configuration

- ExpansionMode：ComboBox；
- SegmentCount：普通 TextBox。

### 8.2 Segments

- Segments：Table；
- SegmentIndex：只读文本；
- RelativeAngle：普通 TextBox；
- Length：普通 TextBox。

Segments 只在全部展开时显示。部分展开仍由模型扩展生成三个管体，但属性表是否显示由 XML 的通用 Visibility 和扩展返回状态共同决定。

### 8.3 下拉选项

    <Options>
      <Option Value="NotExpanded"
              DisplayKey="Models.Hydraulics.Pipe.ExpansionMode.NotExpanded" />
      <Option Value="PartiallyExpanded"
              DisplayKey="Models.Hydraulics.Pipe.ExpansionMode.PartiallyExpanded" />
      <Option Value="FullyExpanded"
              DisplayKey="Models.Hydraulics.Pipe.ExpansionMode.FullyExpanded" />
    </Options>

Value 是模型使用的稳定值，DisplayKey 只负责显示翻译文本。

### 8.4 属性跨组引用

属性定义和属性组分开，使属性可以移动到其他组：

    <PropertyGroup Id="Advanced"
                   TitleKey="Graph.Advanced.Title">
      <PropertyRef PropertyId="SegmentCount" />
    </PropertyGroup>

模型中仍只有一个 SegmentCount，不会因为改变分组而产生重复状态。

## 9. 表单提交和校验

所有数字输入使用普通 TextBox。

属性可以定义：

- CommitPolicy；
- ValidationMode；
- MinimumValue；
- MaximumValue；
- Pattern；
- Required；
- AllowEmpty。

建议默认规则：

- 创建对话框的管段表格使用 Explicit 或行提交；
- 右侧属性栏的角度和长度使用 OnLostFocusOrEnter；
- 输入中间状态不立即判定错误；
- 用户输入负号、小数点或部分数值时不能提前拒绝；
- 提交时先执行通用格式检查，再执行模型扩展业务校验；
- 模型扩展可以为不同属性覆盖提交和校验策略。

同一属性在不同界面可以使用不同策略：

    <PropertyRef PropertyId="RelativeAngle"
                 Presentation="CreationDialog"
                 CommitPolicy="Explicit" />

    <PropertyRef PropertyId="RelativeAngle"
                 Presentation="PropertyPanel"
                 CommitPolicy="OnLostFocusOrEnter" />

## 10. 任务目录和 mdl 单文件

### 10.1 任务目录

Kudo 的任务目录至少包含：

    Manifest.xml
    Task.xml
    Models/
    Assets/

Manifest.xml 说明任务包入口和资源索引。Task.xml 保存任务正文。

### 10.2 mdl 单文件

mdl 是任务目录的压缩单文件形式。压缩包内部仍使用同样的目录和文件名：

    Manifest.xml
    Task.xml
    Models/
    Assets/

目录任务和 mdl 单文件必须经过同一套序列化、反序列化和校验流程。两种形式不能出现两套任务实体定义。

### 10.3 Task.xml 顶层结构

建议顶层结构：

    <Task Format="Kudo.Task/1"
          SchemaVersion="1.0"
          Id="TaskId"
          Title="TaskTitle">
      <CanvasSettings>
        ...
      </CanvasSettings>

      <Viewport Zoom="1.25"
                OffsetX="120"
                OffsetY="80" />

      <Nodes>
        ...
      </Nodes>

      <Groups>
        ...
      </Groups>

      <Edges>
        ...
      </Edges>

      <Annotations>
        ...
      </Annotations>

      <Properties>
        ...
      </Properties>
    </Task>

Format 是任务文档格式标识，SchemaVersion 是文档结构版本，不是模型扩展 ApiVersion 或 ExtensionVersion。模型扩展不在任务文件中声明程序集名或动态库路径。

## 11. Task.xml 数据

### 11.1 画布设置

CanvasSettings 保存网格、端口显示、标签显示、缩略图和 LOD 等任务级设置。

Viewport 保存：

- Zoom；
- OffsetX；
- OffsetY。

缺少 Viewport 时使用 Kudo 默认视口。

### 11.2 通用图元状态

节点保存：

- Id；
- Type；
- Title；
- Description；
- IsLocked；
- Position；
- Size；
- Rotation；
- Appearance；
- Ports；
- Properties。

Type 是稳定的模型标识，不是 C# 类型名。

### 11.3 个性化图元状态

个性化图元使用通用 ExtensionState：

    <ExtensionState SchemaId="SFlow.Hydraulics.Pipe"
                    PayloadType="Binary">
      <Payload>
        ...
      </Payload>
    </ExtensionState>

Payload 由模型扩展编码和解码。Kudo 和业务宿主只负责保存不透明状态，并在打开任务时将状态交给已登记的模型扩展。

模型扩展恢复状态后必须返回：

- 当前属性描述和属性值；
- 端口集合；
- 绘制描述；
- 标签和样式；
- 可用操作；
- 校验结果。

Kudo 不能根据 Payload 猜测业务状态。

### 11.4 属性值

普通属性可以按 PropertyId 保存：

    <Properties>
      <Property Id="Name"
                Type="String"
                Value="Pump01" />
      <Property Id="Locked"
                Type="Boolean"
                Value="false" />
    </Properties>

个性化属性的业务状态由扩展 Payload 保存。属性栏中的 PropertyId 只用于定位编辑请求，不要求 Kudo 理解属性含义。

表格行必须使用稳定 RowId：

    <Row RowId="Segment01">
      <Value PropertyId="RelativeAngle"
             Type="Decimal"
             Value="0" />
      <Value PropertyId="Length"
             Type="Decimal"
             Value="20" />
    </Row>

调整管段数量时，模型扩展负责增加、删除或重排 RowId。不能使用当前行号作为持久化身份。

## 12. 启动配置校验

程序启动时，在模型库正式显示前校验：

1. Models/Model.xml；
2. Models/Symbols/*.xml；
3. 国际化资源；
4. 模型扩展登记；
5. 扩展声明的属性、选项、绘制和端口能力；
6. 文件之间的引用关系。

校验内容包括：

- 文件是否存在；
- XML 是否能解析；
- 根节点是否正确；
- 必填属性是否存在；
- 类型和编辑器是否匹配；
- 标识是否重复；
- PropertyRef 是否引用有效 PropertyDefinition；
- Visibility 是否引用有效属性；
- Option Value 是否重复；
- Column 是否重复；
- 资源 Key 是否存在；
- 引用的图片、SVG 和资源是否存在；
- ExtensionId、NodeType、ElementId 是否冲突；
- 扩展是否能够返回初始描述和投影。

错误的扩展不得导致整个程序崩溃。主程序应隔离无效图元，继续加载其他有效模型，并将完整问题交给诊断界面。

## 13. 打开任务文件校验

打开任务按以下顺序校验：

1. 文件路径和 mdl 包结构；
2. Manifest.xml；
3. Task.xml；
4. CanvasSettings 和 Viewport；
5. 节点标识和节点类型；
6. 节点属性、端口和资源；
7. 连线的源节点、目标节点和端口；
8. 对应模型扩展；
9. ExtensionState；
10. 扩展恢复后返回的属性、端口和绘制描述；
11. 汇总全部问题；
12. 根据问题严重程度进入正常、恢复或诊断模式。

不能遇到第一个异常就退出。单个节点或扩展失败时，应继续检查其他节点，尽量一次性显示完整问题列表。

## 14. 统一问题模型

启动配置问题和打开任务文件问题使用同一结构：

| 字段 | 说明 |
| --- | --- |
| Code | 稳定问题代码 |
| Severity | Info、Warning、Error、Fatal |
| Phase | StartupConfiguration 或 TaskOpen |
| SourcePath | 配置文件或任务路径 |
| Location | XML 节点、属性或行列位置 |
| TargetId | 图元、属性或扩展标识 |
| MessageKey | 国际化资源 Key |
| Arguments | 格式化参数 |
| CanContinue | 是否可以继续 |
| CanAutoFix | 是否可安全自动修复 |
| FixActionId | 处理动作标识 |
| Details | 诊断详情 |
| Exception | 仅写入日志的异常信息 |

问题代码示例：

    ConfigurationFileNotFound
    ConfigurationXmlInvalid
    DuplicatePropertyId
    MissingResourceKey
    MissingReferencedAsset
    UnknownNodeType
    MissingModelExtension
    ExtensionStateInvalid
    PortReferenceNotFound
    ViewportValueInvalid

用户界面显示资源化的简短原因和处理建议，完整异常堆栈写入日志。

## 15. 问题展示和处理

### 15.1 启动阶段

- 没有问题：正常启动；
- 只有 Info 或 Warning：正常启动，并在诊断入口显示数量；
- 有可隔离 Error：显示问题列表，允许继续使用有效模型；
- 有 Fatal：进入安全模式，不加载有问题的配置，但保留诊断和文件处理能力。

问题列表显示：

- 严重级别；
- 问题标题；
- 文件和位置；
- 受影响对象；
- 推荐处理方法；
- 可执行操作。

### 15.2 任务打开阶段

可恢复问题进入恢复会话，不修改原始文件。建议处理方式：

1. 保留原始 mdl；
2. 创建恢复副本；
3. 隔离损坏节点或无效扩展状态；
4. 显示每项问题及处理结果；
5. 对恢复副本再次完整校验；
6. 只有用户明确保存时才覆盖或另存。

缺少模型扩展时，应保留节点和原始不透明 Payload，并将节点置为不可编辑状态，而不是静默删除。

### 15.3 通用处理动作

    OpenSourceFile
    OpenContainingFolder
    CopyDetails
    ReloadConfiguration
    DisableInvalidEntry
    RestoreDefaultValue
    ChooseReplacementAsset
    CreateRecoveryCopy
    ExportReport
    RetryExtension

主程序只提供这些通用动作。模型扩展需要业务专用处理时，也必须返回同样格式的动作描述，不能要求 Kudo 添加业务判断分支。

### 15.4 自动修复原则

自动修复必须：

- 不覆盖用户原始配置或任务文件；
- 生成备份或恢复副本；
- 显示即将修改的内容；
- 修复后重新校验；
- 修复失败时保留原始文件。

默认不自动修复：

- XML 标识；
- 图元类型；
- 扩展 Payload；
- 端口连接；
- 个性化业务数据。

## 16. NativeAOT 约束

Kudo 和宿主必须满足 NativeAOT：

- XML 实体提供明确的保留配置；
- 协议实体提供明确的保留配置；
- 不依赖运行时程序集扫描；
- 不通过 C# 类型名创建模型对象；
- 集合属性使用 AOT 可创建的具体集合；
- 无效输入转换为诊断问题，而不是抛到 UI 线程；
- 目录任务和 mdl 单文件使用相同实体和同一套序列化逻辑。

## 17. 实施顺序

建议按以下顺序实现：

1. 统一问题模型和诊断列表；
2. 增加启动配置校验；
3. 增加任务文件完整校验；
4. 增加恢复副本和诊断报告；
5. 固定 PropertyDefinition、PropertyGroup、PropertyRef；
6. 接入普通图元 Basic 和 Appearance；
7. 接入个性化图元动态属性和表格；
8. 在 Kudo 任务文件中持久化 Viewport；
9. 完成 AOT 发布、异常配置、损坏任务和恢复场景验证。

新增业务图元只能提供通用 XML 数据、国际化资源和模型扩展实现，不能在 Kudo 或业务宿主的通用集成层增加业务分支。
