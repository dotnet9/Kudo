# 包选择与依赖评估

本文件合并 Kudo 工程组合和开源图形建模依赖评估，先说明业务项目如何通过内部 NuGet 包接入 Kudo，再记录参考项目的取舍边界。

﻿# 包选择指南

## 推荐原则

Kudo 以源码形式随本仓库发布，也可通过 `pack.bat` 打包为 NuGet 包供其他项目复用；包依赖全部来自 nuget.org，版本统一在 `Directory.Packages.props` 中锁定。当前 SDK 收敛为 7 个源码工程，不要为了“省事”引用未使用的主题或 3D 包。

| 工程 | 何时引用 | 主要能力 |
| --- | --- | --- |
| `Kudo.Core` | 只处理图模型，不需要 UI | 模型、算法、JSON、文档会话、命令、运行时和校验契约 |
| `Kudo.Avalonia` | 需要桌面图编辑能力 | Canvas、Designer、Dock、属性栏、资源管理及导出打印 |
| `Kudo.Themes.Semi` | 使用 Semi.Avalonia 主题 | Kudo 控件的 Semi 主题资源 |
| `Kudo.Avalonia.3D` | 需要图的 3D 预览 | OpenGL Renderer、软件 fallback、场景构建器 |

## 常见组合

只处理任务 JSON 和图模型：

```xml
<PackageReference Include="Kudo.Core" />
```

完整桌面设计器：

```xml
<PackageReference Include="Kudo.Avalonia" />
<PackageReference Include="Kudo.Themes.Semi" />
```

完整工作台加 3D：

```xml
<PackageReference Include="Kudo.Avalonia" />
<PackageReference Include="Kudo.Themes.Semi" />
<PackageReference Include="Kudo.Avalonia.3D" />
```

`Kudo.Avalonia` 已包含多文档 Dock、属性编辑和导出打印模块；这些能力不再拆成独立包。`pack.bat` 生成全部 SDK NuGet 包，覆盖 `net10.0` 和 `net11.0`，其他项目通过这些包接入。

参数、范围导出、嵌入内容降级和打印 Target 示例见[使用与开发手册](使用与开发手册.md)。

## 版本约束

同一项目内的 Kudo 包应使用相同的版本号。版本由本仓库统一维护在 `Directory.Build.props`；修改包代码或依赖元数据后递增版本并重新打包。规则见[使用与开发手册](使用与开发手册.md)。

Avalonia `12.1.3` 的 Skia 渲染依赖必须与其 `Avalonia.Skia` 兼容：当前统一使用 `SkiaSharp` / 各平台原生资产 `3.119.4`、`HarfBuzzSharp` / 各平台原生资产 `8.3.1.3` 和 `Svg.Skia 5.1.1`。不要单独覆盖到 SkiaSharp 4.x 或 HarfBuzzSharp 14.x；升级渲染栈时需核实 Avalonia.Skia 的实际依赖，并验证 Windows AOT 与 Linux 发布。

## Avalonia 图形建模依赖评估

日期：2026-08-07

## 1. 评估结论

Kudo 继续保持独立实现，不把 FlowGraph、Nodely、NodeEditor 或 Nodify 作为运行时依赖。当前对标重点已经从“补齐基础图编辑能力”转为“收敛内部所有权、建立组合式扩展、完善导出和真实业务验证”。

参考项目只用于验证架构选择、交互细节和性能方案。吸收实现时必须重新适配 Kudo 的模型、命令、任务目录、AOT、内嵌 Avalonia Control 和 Runtime 边界，不直接复制其领域类型。

## 3. Kudo 当前能力

| 能力 | 当前状态 | 主要验证 |
|---|---|---|
| 基础图编辑 | 已完成 | Node、Port、Edge、选择、拖动、Resize、Zoom、Pan、Minimap |
| Edge 系统 | 已完成 | 五类路由、Waypoint、Marker、Label、重连、切割、动画 |
| Group 与 Annotation | 已完成基础闭环 | 非嵌套 Group、折叠代理端点、便签编辑和 Clipboard |
| 历史与权限 | 已完成 | Undo/Redo、只读、`IGraphEditPolicy`、拒绝原因 |
| 扩展边界 | 已完成第一轮 | 五类 Renderer、输入 Behavior、Node Control Registry |
| 多文档与资源 | 已完成 | 任务目录、资源迁移、草稿、Dock 工作区 |
| Runtime 调试 | 已完成基础闭环 | 生命周期、断点、调用栈、变量、Watch、诊断 |
| 大图性能 | 已完成第一轮 | 缓存、Quadtree、裁剪、LOD、Control Host 可见集合 |
| 3D | 已完成可选闭环 | OpenGL、软件 fallback、节点内嵌 3D Control |
| 国际化 | 已完成基础范围 | SDK / Demo 中英文和英文回退 |
| 自动化验证 | 当前通过 | Release 全量测试 611 项通过 |

当前主要差距不是基础功能数量，而是以下开发结构问题：

1. `GraphCanvas` 仍承担大量共享状态和内部协调职责。
2. Runtime、Command 和 PropertiesView 已形成超大实现文件。
3. 模型直接写入、缓存失效、空间索引和 Dirty / Undo 之间缺少统一 ChangeSet。
4. Renderer 是整类替换，属性面板没有标准 Registry，多个领域扩展组合仍需宿主手工编排。
5. 没有独立 PNG、SVG、PDF 导出包。

## 4. FlowGraph

### 4.1 值得吸收

1. Direct Renderer 与 Visual Tree Renderer 的明确分工。
2. Node、Port、Edge、Background 和 Shape Renderer Registry。
3. Shape 数据、Renderer 和交互管理分层。
4. Data Flow Engine 与图编辑 UI 解耦的方式。
5. Virtualization、批量加载和受影响 Edge 路由刷新。

### 4.2 不直接吸收

1. 不用 FlowGraph 模型替换 Kudo 的任务格式和命令体系。
2. 不将全量 Direct Rendering 作为 Kudo 默认模式。Kudo 必须继续保证 TextBox、自定义 Control、无障碍和 OpenGL Context。
3. 不在当前阶段引入通用 Data Flow Executor。Kudo Runtime 继续定位为宿主运行引擎的调试和状态适配层。
4. 不引入 Avalonia 11 或 ReactiveUI 依赖到 Kudo SDK 基础包。

## 5. Nodely

### 5.1 值得吸收

1. UI 无关 Core 与薄 Avalonia 层的依赖方向。
2. Router、PathGenerator、Behavior 和 Renderer 的显式注册。
3. 多个领域包可以组合到同一 Canvas 的 `UseXxxNodes` 模式。
4. Designer Property Registry，以 Descriptor 描述字段、Section 和编辑方式。
5. ADR、研究记录、阶段清单和 Benchmark 报告分离。
6. 不依赖特定 MVVM 框架的核心使用方式。

### 5.2 不直接吸收

1. 不复制全部领域包。Kudo 先用两个内部示例模块验证扩展组合，再决定是否发布独立领域包。
2. 不通过大量 `NodeModel` 子类建立序列化多态。Kudo 继续优先使用 `NodeModel.Type + Properties + Registry`，保持 AOT 和任务格式简单。
3. 不直接比较 Nodely 的约 15 ms 路由数字与 Kudo SmartOrthogonal。二者的 Router、障碍质量和 workload 不一致。

## 6. NodeEditor

### 6.1 值得吸收

1. Model、UI、MVVM 三层职责边界。
2. Node 和 Connector Segment 的增量 R-tree 命中维护。
3. Move、Resize、Rotate 分离为独立 Behavior。
4. Ink 数据、输入层和转换命令分离。
5. PNG、SVG、PDF 等导出能力放在独立 Renderer / Storage 边界。
6. 将路由、命令、Transform、Export 等能力拆成专题文档。

### 6.2 不直接吸收

1. 当前不开发 Rotate 和 Ink。Rotation 会同时影响端口位置、Edge 路由、空间索引、Group Bounds、选择框和内嵌 Control。
2. 不绑定 NodeEditor 的 MVVM 类型、CommunityToolkit 或 Newtonsoft.Json 契约。
3. Export 参考其职责划分，但 Kudo 导出必须复用自己的路由、Marker、Group、Annotation 和 Renderer 语义。

## 7. NodifyAvalonia

### 7.1 值得吸收

- MVVM 绑定方式。
- 自动平移、选择、拖动和连接的交互细节。
- 大量 StyledProperty 暴露可配置行为的经验。

### 7.2 当前定位

Kudo 已独立完成自动平移、连线切割、Push Items、重连、Waypoint 和统一策略，因此 NodifyAvalonia 主要作为交互回归参考，不再作为架构主线。其本地源码仍基于 Avalonia 11.1.0，也不适合作为 Avalonia 12 的直接依赖。

## 8. 配套组件边界

| 项目 | 当前用途 | 边界 |
|---|---|---|
| Avalonia | UI 和 Headless 测试 | 不进入 Core、Algorithms、Serialization、Runtime |
| Dock.Avalonia | 多文档工作区 | 仅进入 Docking 和 Demo |
| Semi.Avalonia | 默认主题 | 仅进入 Themes.Semi 和 Demo |
| Ursa.Avalonia | 对话框和高级控件 | Designer / Demo 按实际需要引用，不进入 Core |
| CodeWF.AvaloniaControls | Desktop Demo 窗体和 Dock 主题 | 不作为 Kudo 基础 SDK 依赖 |
| Silk.NET.OpenGL | 3D Renderer | 仅进入 Kudo.Avalonia.3D |
| SkiaSharp | PNG、SVG、PDF 离屏输出后端 | 仅进入 Kudo.Avalonia，避免反向污染 Core |

## 9. 当前吸收顺序

1. 参考 Nodely 的 Registry 和 Property Descriptor，设计 Kudo 可组合扩展机制。
2. 参考 FlowGraph 的 Renderer 分工，将 Canvas 渲染组织继续下沉，但保留混合 Control 路线。
3. `Kudo.Avalonia.Export` 模块已按 NodeEditor 的职责边界完成第一轮实现，继续用固定文档和 Poppler 做格式回归。
4. 使用 FlowGraph、Nodely 和 NodeEditor 的空间索引方案复核 Kudo 增量失效设计。
5. NodifyAvalonia 继续用于成熟交互的回归对照。

## 10. 明确不做

1. 不添加上述项目的运行时 PackageReference。
2. 不复制其命名空间、公开模型或序列化格式。
3. 不因为第三方有功能就自动建立 Kudo Phase。
4. 不用 Demo 性能或单次 Stopwatch 数字作为跨项目优劣结论。
5. 不在没有业务执行语义时把 Kudo Runtime 扩展成通用工作流引擎。
